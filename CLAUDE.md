# Pitchframe — context for Claude Code

You are working **on** Pitchframe, not using it. This file is the orientation;
read it before changing anything.

If you were asked to *make a video for this project*, that is different — invoke
the `pitchframe` skill instead.

---

## What this repo is

Two things shipped together:

1. **A Claude Code plugin** — skills, subagents and a slash command that teach an
   agent how to make a launch video from a codebase.
2. **An npm package** (`npx pitchframe install`) that scaffolds a Remotion
   project into a user's repo and installs the plugin into `.claude/`.

The agent does the reasoning. The npm package is an installer, not an
orchestrator. Nothing in `bin/` calls a model.

---

## The one idea everything serves

**Pitchframe makes launch videos, not demo videos.**

- A **demo** answers *what does this product do?* It tours features. It reads as
  documentation.
- A **launch** answers *why should this product exist?* It shows one moment that
  embodies the answer, framed cinematically and held with intention.

Raycast AI, the original v0 launch, Cursor's early videos, Linear's cycles
announcement — none list features. Each shows one moment; everything else is
setup and payoff around it.

This is not a style preference. It is the constraint the whole design encodes,
and most of the invariants below exist to stop the system drifting back toward a
demo. **An earlier version of this repo had `feature`, `chapter`, `montage` and
`stat` beat types and produced a 90-second feature tour. They were deleted on
purpose.** If you find yourself adding a beat type so a plan can show one more
thing, you are rebuilding that mistake.

## Repo map

```
pitchframe/
├── skills/            # what the agent knows. One directory per pipeline step.
├── agents/            # subagent definitions — these pin the per-step model
├── commands/          # the /pitchframe slash command
├── bin/pitchframe.mjs # the installer CLI
├── scripts/           # recon, extract-palette, apply-palette, capture, gen-audio
│   └── lib/recorder.mjs #   CDP screencast + action driver + cursor track
├── template/          # the reference Remotion project, copied into user repos
│   ├── plan.json      #   the scene plan — this IS the video
│   ├── palette.json   #   extracted colours, strict JSON
│   └── src/           #   composition + beats + theme.ts (generated)
└── docs/              # architecture, doctrine, extension guide
```

`scripts/` is duplicated into `template/scripts/` for local development so the
scripts can find `palette.json` at the path they'll have once installed. **When
you change a script in `scripts/`, copy it to `template/scripts/` too**, or your
local test runs the old one.

## The three contracts

Everything flows through these. Break one and the pipeline breaks silently.

**`.work/direction.json`** — **the frame.** Generated by
`scripts/art-direction.mjs` *before* the Director runs, and binding on it:
palette style, structure, type layout, accent, transition, hero framing
grammar, drawn archetypes, 3D placement. Derived from the product, and checked
against every previous run in `runs/` so a look is never repeated. The Director
may override a single field with a written reason; silently substituting its
own taste is the failure this replaced.

**`script.json`** — **the spine.** Written by the Director; everything else
obeys it. Each line carries what is *said* and what is *shown* together. This is
the file the judge edits, and the only file where creative decisions live.
It decides what is *said and shown*, never how it *looks* — that is the
direction's job, and keeping them apart is what stopped every video from
converging on the same template.

**`plan.json`** — **generated** from `script.json` + measured voice durations by
`plan-from-script.mjs`. Do not hand-edit it; edit the script and re-cut. The
video. Four beat types only: `typography`, `logo`,
`interaction`, `cta`, plus `ui` for a single establishing shot. Beats are
contiguous: each starts where the previous ended, first at 0, last ending exactly
at `total_frames`. Defined in `template/src/lib/types.ts`; documented in
`skills/pitchframe-launch-video/SKILL.md`. **Change one and you must change the
other.**

**`palette.json`** — five keys, all hex or null:
`{ background, text, primary, accent, logo_color }`. Data, never prose. Produced
by `scripts/extract-palette.mjs`.

**`src/theme.ts`** — **generated**, by `scripts/apply-palette.mjs`. The only
place in the composition where a colour is written down. Never hand-edit it;
never put a colour literal in a component.

**`public/assets/<name>.track.json`** — **generated**, by the recorder. The
cursor path and mouse events for a screen recording, one entry per frame.
Deliberately not in `plan.json`: it is hundreds of points that no human reads
and no agent writes, and the plan has to stay reviewable. Loaded at render time
through `useJsonAsset`.

**`public/audio/audio.json`** — **generated**, by `scripts/gen-audio.mjs`.
Says which of `cues.wav` / `bed.wav` / a user's `music.mp3` exist. The
composition reads it rather than assuming, so a render on a fresh clone is
silent instead of broken.

### The two generated-audio rules

The score is *derived from the plan*, not authored. So:

- **Re-run `gen-audio.mjs` whenever a frame number changes.** Otherwise the
  click sound stays where the old edit was, and a video with one misplaced cue
  reads as entirely out of sync.
- **Nothing in the audio path may use `Math.random()`.** The noise generators
  are a seeded LCG on purpose — random noise means re-rendering the same plan
  produces a different file every time.

## Invariants

Verify these still hold after any change:

| Invariant | Why | How to check |
|---|---|---|
| Zero colour literals in `template/src/**/*.tsx` | Otherwise two products' videos look identical | `grep -rnE '#[0-9a-fA-F]{3,8}\|rgba?\([0-9]' template/src --include=*.tsx` → only `theme.ts` |
| Exactly one `interaction` beat per plan | Two hero moments means neither gets proven | critique skill, check 1 |
| Hero beat ≥ 30% of `total_frames` | Below that it's a feature, not a spine | critique skill, check 3 |
| Every plan has a payoff beat | Without it the hero is a screenshot, not a claim | critique skill, check 4 |
| `theme.ts` regenerated per product | Same colours across products = the pipeline is broken | render one frame under two palettes; they must differ byte-wise |
| No springs, bounces or elastic easing | Reads as template, not film | `template/src/lib/motion.ts` is the only source of curves |
| One camera system | Two drift apart and shots stop matching | `grep -rn "perspective" template/src` → only `Stage.tsx` |
| Every `delayRender` is continued on **both** the resolve and the catch | A missing asset must fall back in ms, not hang until render timeout | `grep -n "delayRender\|continueRender" src/lib/asset.ts` → one delay, two continues |
| Camera moves only via `SHOTS` | Freeform camera math means a different video every run | `grep -rn "rotateY\|translate3d" template/src` → `camera.ts` / `Stage.tsx` |
| Every scene that renders text reads colour from `surfaceColors()` | White type on a light mesh is 1.57:1 | `grep -ln "surfaceColors" template/src/scenes/*.tsx` → typography, cta, logo, ui |

## The hero beat's arithmetic lives in `lib/heroShots.ts`

`resolveShots` → `shotAt` → `frameShot`, all pure. Given a beat, a length and a
frame, every number is determined without mounting anything.

It was extracted because `InteractionBeat` had reached 665 lines and the
depth-of-field bug that blurred a whole video survived three renders inside it.
A file too big to hold in your head is a file bugs hide in. Keep the maths out
here and the component as an orchestrator.

**`resolveShots` is the only place the shots-vs-beat-fields precedence
exists.** Do not re-implement it.

## Audio leads, picture follows

`gen-voice.mjs` runs **before** `plan-from-script.mjs`, and that order is load
bearing. Beat lengths are the *measured* durations of the spoken lines — nobody
chooses them. Plan the picture first and the voice drifts against it.

Duration is `bytes / (24000 × 2)` because Maya returns raw PCM. Nothing needs to
*hear* the audio to sync it.

**`MAYA_API_KEY` comes from `pitchframe/.env` or the environment. Never commit
it, never put it in a plan file** — this repo is meant to be published.

**A missing key stops the run.** It used to skip with a one-line notice, and
the consequence was four consecutive silent videos whose beats were timed by a
reading-speed guess — no voice, no sync, no audio, and nothing anywhere said
the headline feature had not run. `--allow-silent` opts out deliberately.
Generalise it: **an opt-in feature that degrades silently is a feature that
never runs.**

## Every run is archived

`scripts/archive-run.mjs` copies the script, plan, palette, direction, video
and feedback into `runs/<product>-<timestamp>/` after each render.

This is not bookkeeping. `runs/` is the *input* to `art-direction.mjs`, which
reads every archived `direction.json` and rotates away from any look already
used. No archive → no history → no way to detect that this video looks like the
last three, which was the single most persistent complaint about the output.

## Renders are *nearly* deterministic

Re-rendering the same frame usually gives a byte-identical PNG, but not
always — one run in three produced a PNG differing by ~150 bytes out of 300KB
on a frame with no animation left to settle. Cause not yet found; suspect
compositing of a `backdrop-filter` layer.

It matters for one thing only: **do not verify a refactor with a single
render.** Render the same frame two or three times before concluding a
difference is a regression. Everything the pipeline *generates* — audio noise,
particle placement, stack rhythms — is seeded and genuinely deterministic.

## Making changes

**Typecheck** (the fastest signal — run it after every edit):

```bash
cd template && npx tsc --noEmit
```

**Render a frame** to see a change:

```bash
cd template && npx remotion render LaunchVideo out/f200.png --frame=200
```

**Render times, measured on this machine** (1920×1080, ANGLE, warm cache):

| | Per frame |
|---|---|
| 2D | 172 ms |
| 3D (`three_d` treatment) | 321 ms — **1.9×**, not the order of magnitude usually assumed |

A 3-second 3D beat adds ~13s. A 20s video: ~113s all-2D, ~126s with one 3D
beat. Measure *warm* — the first render after touching the Three.js path pays
15–20s of one-time bundling and shader compilation, and measuring cold gives
numbers that are not just wrong but nonsensical (a 60-frame render finishing
faster than a 30-frame one).

**Render the whole thing** (~60s for 22s of video):

```bash
cd template && npx remotion render LaunchVideo output.mp4
```

**Regenerate the theme** after touching `palette.json` or the generator:

```bash
cd template && node scripts/apply-palette.mjs
```

**Prove the palette pipeline still works** — the one test that catches the worst
class of regression:

```bash
cd template
node scripts/extract-palette.mjs --url https://example.com && node scripts/apply-palette.mjs
npx remotion still LaunchVideo out/a.png --frame=200
node scripts/extract-palette.mjs --url https://linear.app && node scripts/apply-palette.mjs
npx remotion still LaunchVideo out/b.png --frame=200
# a.png and b.png must differ
```

## Gotchas that have already cost time

Each of these was a real bug that rendered without error and only showed up in
the output.

- **`radial-gradient(circle 34% at …)` is invalid CSS.** `circle` takes a
  length, not a percentage — the whole gradient is dropped, so the mask never
  applies. This silently disabled the focus pull entirely and made the hero
  zoom blur its own subject. Use `ellipse W% H%`.
- **`#0000ee` is the browser's default unstyled-link colour**, not a brand
  colour. It is saturated and frequent, so any frequency-ranked extraction puts
  it first. Declared CSS custom properties beat counting pixels.
- **A light-themed product declares near-black text.** The background gets
  forced dark, so text must be flipped *before* deriving anything from it —
  otherwise "lighten the accent toward the text colour" walks it toward black.
- **Adding a light surface does not recolour the type on it.** The first
  `light` beat rendered white display type on pale lavender at **1.57:1** —
  fine on a design mock, invisible in the video. Any component that can sit on
  a bright beat has to switch to `TEXT_ON_LIGHT` / `ACCENT_ON_LIGHT`. This is
  the same failure as the flip above, one layer up, and it will recur every
  time a component gains a light context.
- **The reference films are mostly drawn, not filmed.** Only one of the six is
  largely real footage; the rest rebuild their UI as vector and animate it a
  piece at a time. Pitchframe was the inverse ratio, and that mattered more
  than framing or colour. A shot can carry `render` instead of framing the
  footage — but **the hero stays real**, and every drawn label must exist in
  `.work/recon.json`. A rebuilt component with the product's real words is
  truthful; one with invented words is a lie that renders beautifully.
- **`bleed` deletes edge-anchored UI, and no value of it is safe.** At 2360 it
  cropped 9.3% a side and removed a canvas app's toolbar and sidebar entirely —
  the shot was a white field with one shape and the product was invisible.
  Reducing it to 2120 (4.7% a side) brought the sidebar back and still lost the
  toolbar. Bleeding *is* showing less than the whole app; for products whose
  chrome lives at the edges the answer is `contained`/`chrome`, not a number.
- **Three's `TextureLoader` cannot load an SVG.** It goes through `ImageLoader`,
  and an SVG with no intrinsic pixel size decodes to a zero-sized image; WebGL
  gets an empty texture and reports nothing. The mark vanishes, the material
  switches to its textured colour, and the result is a dark slab on a dark
  background — a black frame with no clue why. `useThreeTexture` rasterises SVG
  to a canvas at an explicit size first. This only began mattering when logo
  fetching started preferring inline SVG, which is the better asset everywhere
  else.
- **A capability nothing asks for is never used.** Three.js shipped built,
  typed, documented and wired to the schema, and no plan invoked it once. The
  skills said "you may". Defaults and critique checks are what actually cause
  a thing to happen.
- **Depth of field must be tied to the lens that motivates it.** `zoomBlur`
  ramped to a fixed 4px independent of `zoomPeak`, so setting `zoom: 1` to
  disable the punch left the blur running — and because the sharp spot is a
  small ellipse at `zoom_target` (defaulting to the *click target*), a shot
  aimed at a toolbar blurred the whole rest of the app. The product looked out
  of focus for most of the hero and nothing in the plan said why. A lens that
  does not move has no falloff.
- **Bloom hurts bright products.** Screening a blurred bright copy over a white
  canvas cannot lift white further, so all it does is halo the dark strokes and
  soften everything. `Grade` now defaults `bloom` to 0; pass it explicitly for a
  dark-heavy video.
- **A motion trail has to be legible *as copies*.** The first `ghosted` layout
  used a diagonal 26/14px offset with 1.6px of blur per echo against 150px
  display type — that reads as a drop shadow, not a trail. Lateral only
  (diagonal fights the baseline), roughly a third of the cap height, and
  barely any blur.
- **A fan needs displacement on the order of a quarter of the card.** The first
  `VectorFan` offset each card by 54px against a 900px card — 6%, which is not
  a fan, it is a stack with a printing error, and the titles landed on top of
  each other. Lateral offset and *progressive* rotation are what splay it;
  z-depth alone just makes cards smaller.
- **`AbsoluteFill` inside `Stage` collapses to a point.** Stage's inner element
  is sized by its transform and has no width of its own, so `inset: 0` gives
  zero size and every percentage-positioned child lands on the same spot. Give
  drawn content an explicit 1920×1080 box.
- **A hero held on one framing is the "this was generated" tell.** Bigger than
  colour, bigger than easing. Sixteen samples of a reference launch film gave
  sixteen different compositions; three Pitchframe videos in a row held one
  window for thirty seconds and looked like the same video recoloured. The
  hero takes a `shots` array cut from one continuous recording — see
  `HeroShot` in `lib/types.ts`.
- **A default can silently revert a fix.** `chrome` defaulted to `macos`, and
  chrome forces `contained` geometry — so the framing work landed and was
  undone in the same session, across three videos, while the skill still told
  the agent `bleed` was the default and the critique still flagged `contained`
  as wrong. When a default contradicts a skill, the default wins and nobody
  notices. Check both.
- **A crop is not a centred slice.** Sizing a container to the crop's own
  aspect and placing the footage inside it is exact at any crop position; a
  16:9 slice centred on the crop runs off the image near an edge and fills
  with empty panel.
- **A contained panel is the "this was generated" tell.** A screenshot centred
  in a rounded card with margin on all four sides reads as a slide, and no
  camera work fixes it. `framing` defaults to `bleed` for this reason — the
  default is the opinionated option on purpose.
- **Interaction capture must reject identical before/after frames.** A hero beat
  dissolving between two identical screenshots looks like the product did
  nothing, which is worse than having no hero beat.
- **`networkidle` never fires** for apps with websockets or streaming. Use
  `domcontentloaded` plus an explicit content check.
- **A solid-black 3840×2160 PNG compresses to ~29KB**, so file size cannot
  detect a blank screenshot. `capture.mjs` measures luminance variance instead.
- **Framework-generated element ids look like good selectors and are not.**
  React emits `:r3:`, `_r_d_`, and `base-ui-_R_3b9ai86nab6lqa_` depending on
  version and library; all change on the next build. `recon.mjs` filters on
  *shape* — short, mostly alphabetic, at most a digit or two — because two
  earlier filters keyed on known prefixes and both were defeated within a day.
- **GSAP's obvious Remotion pattern is silently broken.** Building a timeline
  in `useMemo` hands GSAP `null` refs — `useMemo` runs during render, before
  refs attach — and it tweens nothing without erroring. Always go through
  `lib/useGsapTimeline.ts`, which uses `useLayoutEffect` for both the build
  and the seek.
- **Vite binds `::1`, not `127.0.0.1`.** Probe both or you'll conclude a working
  dev server never started.
- **A CDP screencast emits frames at the viewport's CSS-pixel size**, ignoring
  `deviceScaleFactor` entirely — `maxWidth` is a ceiling that only ever scales
  *down*. Asking for 2× on a 1440 viewport still returns 1440. The viewport is
  the only lever on footage resolution, which is why `RECORD_VIEWPORT` is sized
  against the composition's framing rather than being an arbitrary default.
- **A screencast contains no mouse cursor.** `mouse.move()` moves an invisible
  pointer. The recorder logs coordinates to a track and the composition draws
  the cursor as a layer — which turned out better than injecting one into the
  page, since it stays sharp under the zoom and the ripple lands on the exact
  press frame.
- **`filter` and `backdrop-filter` collapse 3D on the element that carries
  them.** An entrance blur applied inside `<Stage>` silently flattens the whole
  camera. Effects go on leaves, or on a wrapper *outside* the stage.
- **Chrome only paints when something changes**, so a screencast of a still page
  produces almost no frames. The recorder resamples to a fixed fps and holds —
  correct, because the screen really was static. But it means `distinct_frames`
  is the only honest measure of whether a recording captured anything.
- **Frames must be acknowledged or Chrome stops sending them** — including the
  ones you discard past the memory cap.
- **`radial-gradient(circle 34% at …)` is invalid CSS** (see above), and the
  same class of silent failure applies to any mask: if a mask string is
  malformed the element is drawn *unmasked*, not undrawn.
- **A glob inside a block comment ends the comment.** `runs/*/direction.json`
  in a `/** … */` header contains `*/`, so the comment closes mid-sentence, the
  remaining prose parses as code, and a backtick further down opens a template
  literal — producing `SyntaxError: Unexpected identifier '$'` pointing at a
  line thirty lines away that is perfectly valid. Write `runs/<name>/…` in
  comments. `node --check` on every script catches it in a second.
- **Variety cannot be prompted for.** Five palette styles, three surfaces,
  three type layouts, four framings, eight camera moves, two drawn archetypes
  and a 3D treatment shipped, and every video still came out looking the same,
  because each individual choice was defensible in isolation and nothing could
  see across runs. Telling the Director to "be varied" changed nothing — it has
  no memory of the last video. The fix was mechanical: choose the look in a
  script, derive it from the product, and diff it against archived runs. Any
  future "make it more X" instruction aimed at a model's judgement will fail
  the same way; make it checkable or it will not happen.

## Conventions

Match the surrounding code. Comments explain *why*, never *what* — the
non-obvious constraint, the failure mode being prevented, the reason a number is
that number. Every magic value in `motion.ts` and the beat components has a
reason; keep it that way.
